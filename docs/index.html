01 — Abstract & contributions

Language correctness does not imply physical feasibility.

A robot can correctly transcribe “bring the blue bottle and return” yet fail because the object is missing, the map is stale, the path is blocked, or grasp has not been verified. S2SC proposes a typed and monitored interface between probabilistic language modules and physically grounded robot skills.

We separate symbolic decoding from perception, static type checks from runtime safety, task planning from motor control, and experiment hypotheses from empirical results. The first artifact is a deterministic browser grid-world, designed to make failure cases and evidence visible.

C1

Bounded language bridge

ASR / direct SLU plus optional CVNSS4.0 FST and TinyLM rescoring. Neither component commands motors or asserts physical truth.

C2

Typed Task IR

Explicit versions, units, constraints, provenance and an unprivileged PROPOSED state with validation and rejection.

C3

Evidence-based grounding

Object class, visual observation age, localization, path existence, payload affordance and battery reserve.

C4

Skill contracts & verification

Bounded planning, action feedback, failure codes, postcondition tests and independent safety intervention.

03 — Why world grounding matters

From a word to a physical referent.

“Blue bottle” is an unresolved linguistic reference until the robot can associate it with a sensed object, a localization frame, a sufficiently recent observation and a feasible skill. Grounding is not a single VLM yes/no prediction; it is an evidence chain that must remain valid while acting.

G₁

Referent binding

Does a detected object match type, color and location? Is this the correct instance among distractors?

Output: bound object ID + observation score
G₂

Pose & time

Is the map frame known? Is the pose recent? Are observation and robot frames consistent?

Output: frame, timestamp, uncertainty
G₃

Affordance

Can this robot reach and manipulate that object given payload, geometry, obstacles and energy?

Output: admissible skill preconditions
G₄

Runtime revalidation

Recheck moving obstacles and postconditions. Grounding can become stale between check and use.

Output: continue / replan / stop
Admit(T,W) = WellTyped(T) ∧ Grounded(T,W) ∧ Authorized(T) ∧ Feasible(T,W) ∧ Fresh(W)

This is a software admission predicate, not a formal guarantee of functional safety in a physical environment.

05 — Base27 & ternary representation

27 symbols. Three trits.
No magical compression.

With the illustrative alphabet A–Z plus SPACE, each symbol ID belongs to [0,26] and has a unique three-trit radix-3 representation (3³=27). The same digit sequence offset by −1 can be displayed as a balanced-trit tuple.

A 27-way symbol can also be stored in 5 binary bits. Three trits stored independently in two-bit fields need 6 bits; three-trit mathematical notation alone does not reduce FPGA BRAM, DSP count or MAC operations. This panel does not convert Unicode Vietnamese into CVNSS4.0.

06 — Experimental protocol

Measure the entire mission.
Do not optimize an unproven claim.

VariantLanguage front-endSame grounding / skillsPrimary question
B0Direct Vietnamese SLUYesIs ASR even necessary for bounded commands?
B1Unicode ASR + typed parserYesBaseline transcription-based system
B2Unicode ASR + context modelYesGain from contextual reranking alone
B3Unicode ASR + CVNSS-FST + TinyLMYesIncremental benefit or cost of CVNSS
B4Phoneme / tone ASR + intent headYesIs phonetic output a better bridge?
MEASURE

Speech → action reliability

Intent accuracy, slot F1, calibration, out-of-domain rejection, false execution, grounding false acceptance, grasp and return success, full mission success.

PROFILE

FPGA–ARM economics

Controller deadline misses, p95/p99 latency, execution energy, LUT, FF, BRAM, DSP, timing closure, power and model-memory footprint against CPU/MCU baselines.

Results status: No real ASR WER, FPGA timing closure, BRAM savings, trained TinyLM, drone flight or certified safety results are claimed in this preprint release. Establish a CPU/MCU baseline, then run a documented ablation and hardware-in-the-loop study.
